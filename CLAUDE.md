# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A 2D, two-phase (water/oil), immiscible toy reservoir simulator using two-point flux approximation (TPFA), translated from the Matlab codes of Aarnes, Gimse & Lie (kept in `matlab_codes/`, paper in `refs/aarnes2007introduction.pdf`). Incompressible by default (`ct = 0`), with optional slight compressibility (`ct > 0`, backward-Euler accumulation term in the pressure equation, and the corresponding storage term in the transport equation, charged to the phases in proportion to their saturation — ref `ResSim.storage_rate`). The Python code is verified to reproduce the Matlab output — the regression values in doctests and tests encode this, so do not "fix" numeric expected values unless the physics intentionally changed.

## Downstream usage

The main consumer is [patnr/HistoryMatching](https://github.com/patnr/HistoryMatching) (locally at `~/P/HistoryMatching`), an ensemble history-matching tutorial that uses `ResSim` as its forward model. Consequences for changes here:

- It pins this repo by **git commit hash** in its `requirements.txt` (with a commented-out `-e` local-path line for development), so changes here don't break it until the pin is advanced — but breaking changes should be flagged so the pin advance can be coordinated. E.g. its notebooks call `model.sim(dt, nTime, wsat0, pbar=False)` expecting a single array (v0.2.0 returns an `(S, P)` tuple), and use the pre-unification well API (`inj_xy`, `prd_rates`, `nInj`, `actual_rates["prd"]`, ... — replaced in v0.3.0 by the unified, signed-rate well API, which now lives on a `Wells` object: `model.wells.xy`, `model.wells.rates`, `model.wells.actual_rates`, ...); both will require updating the notebooks when the pin advances.
- Its de facto API surface is wider than `sim()`: the well config (`model.wells.xy`, `model.wells.rates`, ..., incl. the singleton time-broadcast behaviour), grid conversions (`xy2ind`, `ind2xy`), `shape`/`Nxy`, and the plotting mixin (`plt_field`, `plt_production`, `anim`). Notably it **mutates `TPFA_ResSim.plotting.styles`** to register its own field styles — treat that dict and the `plt_field(style=...)` mechanism as public API. (The `unit` key added to `styles["default"]` is therefore optional and merge-safe: a style dict lacking it inherits the `None`.)
- Ensemble forecasting is why `ResSim` is OOP with per-instance state (see below), and why `sim` accepts `pbar=False`: many instances/runs, no shared mutable state, quiet loops.

## Commands

Dev environment is managed with uv (`uv sync`), but a plain `pip install -e .` also works. Note: `mise.toml` sets `UV_PROJECT_ENVIRONMENT` so the venv lives at `~/.cache/venvs/TPFA-ResSim`, not in-project — if mise isn't active in your shell, export that variable before running uv to avoid creating a duplicate `.venv`.

Plain `uv sync` installs the default (`dev`) group, i.e. everything. CI instead installs
only what it runs, via the narrower `test` and `docs` groups that `dev` includes — which
keeps the interactive tools out of the CI environment, notably `pdbpp`, whose shadowing of
the stdlib `pdb` that pytest and `doctest` import can break *collection* on an interpreter
it dislikes. It does the installing and the running in **one** step, e.g.
`uv run --locked --no-default-groups --group test pytest`: since `uv run` syncs
implicitly, a separate `uv sync` step would have to be undone with `--no-sync` in the
next, stating the group selection twice — so don't reintroduce one. Locally none of this
applies: plain `uv run` is right (as the commands below), its implicit sync converging on
the `dev` group you want.

- **Run all tests**: `uv run pytest` (no further args). `addopts` in pyproject.toml makes this run `tests/` **plus doctests** in all `TPFA_ResSim` modules (`--doctest-modules`). Doctests are part of the test suite.
- **Run a single test**: override addopts, e.g. `uv run pytest -o addopts="" "tests/test_examples.py::test_example[quarter_five_spot]"`
- **Lint**: `uv run ruff check` (config in pyproject.toml; max line length 88; deliberately permissive about operator/array alignment — preserve the aligned formatting style used in the code).
- **Type check**: `uv run ty check` (clean). ty cannot verify `**dict` splatting into a typed signature, so the examples' splatted dicts (`grid`, `kws`, ...) carry a bare `: dict` annotation to opt out of that check -- keep it when adding such a dict. Not run in CI — CI lints with `uvx ruff check` only. NB: ty narrows an `Any`-declared attribute to whatever was last assigned to it, so it cannot see through the `__setattr__` normalization — e.g. `model.wells = [records]` followed by `model.wells.names` reads as a `list`. Route the assignment through an `Any`-annotated local if that matters.
- **Docs**: `uv run pdoc --math -o docs/ ./TPFA_ResSim` (published to GitHub Pages by `.github/workflows/docs.yml`). Docstrings are pdoc-flavoured markdown with LaTeX math; `TPFA_ResSim/README.md` is included into the package docstring via `.. include::`.

The supported Python range is whatever `requires-python` in pyproject.toml says (currently `>=3.12`); the floor tracks Colab's Python so the package installs there without re-installs. CI tests 3.12–3.14 on ubuntu + macos.

## Architecture

The package is six files; the physics lives in `TPFA_ResSim/__init__.py`:

- **`ResSim`** (`__init__.py`) is a dataclass composed by multiple inheritance: `ResSim(AlignedRepr, Grid2D, Plot2D)`, and *composing* a `Wells` (`wells.py`). OOP is used (rather than passing dicts) so ensemble forecasting (as in HistoryMatching) can hold independent instances whose parameters don't influence each other.
  - `sim(dt, nSteps, S0, P0=None)` is the entry point, returning the `(S, P)` saturation and pressure trajectories: it loops `time_stepper`, which per step solves pressure (`TPFA()` → sparse direct solve; elliptic if `ct == 0`, else parabolic backward-Euler) then transports saturation with either the explicit upwind scheme (`saturation_step_upwind`, sub-steps from a CFL estimate) or the implicit Newton–Raphson scheme (`saturation_step_implicit`, halves sub-dt until convergence).
  - Method names reference listings in the paper (e.g. `TPFA()` = Listing 1, `RelPerm()` = Listing 6).
  - **What stays here, of the wells**, is what couples them to the reservoir or to the linear system: `assemble_wells` (which writes the source field `_Q` and the bundle `_wells_now`), `realize_bhp`, `bhp` (needs `RelPerm`), and the `well_controls` hook. Everything else is `wells.py`. `ResSim.nComp` forwards `Wells.nComp`, the equations being assembled per completion.
  - **Wells are one unified set** — there is no code-path distinction between injectors and producers. `wells.rates` is **signed**: positive injects (water), negative produces (at the cell's fractional flow); the transport step discriminates by the sign of `_Q`, not by well identity. A BHP-controlled well's flow direction is likewise emergent (`realize_bhp`), and plot markers are inferred from the sign of the rate spec. `wells.actual_rates`/`actual_bhp` are single `(nComp, nSteps)` arrays.
  - **`__setattr__` does normalization magic**: scalar `K` is broadcast to shape `(2, Nx, Ny)`; `K`/`por` get their grid-shaped defaults here when left `None` (which is why there is no `__post_init__`); and `wells` accepts either a `Wells` or the records to build one from, binding it to this model either way. The well arrays' own normalization is `Wells.__setattr__`. When `ct == 0` (and no BHP-controlled well), the rates must sum to zero at every time index (asserted in `time_stepper` — otherwise mass imbalance would silently leak in the SW corner). With `ct > 0` the imbalance is absorbed by storage (enabling e.g. primary depletion by a lone producer).
  - `well_controls(S, P, k)` is the designed override point (patch/subclass) for feedback control (e.g. shutting wells based on saturation): it returns `dict(rates=..., bhp=...)`, so an override can set the wells' *modes* too, thereby approximating the control-mode switching (e.g. a rate target with a BHP limit) that the model does not do natively — ref `examples/well_control.py`. Note that with `ct == 0` an override must keep injection and production balanced. It replaces the `dynamic_rate` hook of v0.2.0.
  - **`cdarcy`** is the whole of the units story: the equations carry **no conversion factors**, so any *coherent* system (SI, or the examples' unnamed `1`s) just works, and a *practical* one (metric: m, day, bar, mD, cP) needs only this constant, $C = u_k u_p u_t / (u_μ u_L^2)$ ($0.008527$ for metric, i.e. ECLIPSE's `CDARCY`). It enters at exactly **two sites** — the transmissibilities in `TPFA` and the well index in `peaceman_WI` — while the `ct` accumulation term, the transport scaling and `estimate_1CFL` are built from those and were already consistent, so **do not add factors elsewhere**. The rate unit is thereby forced to $u_L^2/u_t$, an *areal* rate (per unit thickness); $C$ neither names nor determines the units, being one scalar over five choices. Pinned by `tests/test_units.py`, which poses one reservoir in SI, metric, field and lab units and demands agreement. Deliberately *no* unit machinery: no `UnitSystem`, no registry, no plot labels — a `UnitSystem` + label layer was written and rejected as over-built.
- **`Grid2D`** (`grid.py`): rectangular grid geometry and the coordinate/index conversions (`xy2ind`, `sub2xy`, ...). Index ordering is **C-major (numpy default), unlike the Matlab original**: `x` is the first axis, so printing a field matrix shows x as the row index, whereas plots show x left→right, y bottom→top. This ordering is hard-coded in the simulator via `ravel`/`reshape`.
- **`Wells`** (`wells.py`): the wells, as a dataclass held at `model.wells` — the flat, per-*completion* arrays (`xy`, `rates`, `bhp`, `WI`, `group`, `names`, `actual_rates`, `actual_bhp`) plus the reporting derived from them (`nComp`/`nWell`, `rates_by_well`, `signs`, `at_time`). Alongside it, two **free functions** — `peaceman_WI(model, xy, rw, skin)` and `well_path(model, vertices, rw, skin)` — taking the model for its grid and `K`. Deliberately not methods: they are *calculators*, not accessors, and the signature says so — what they return must be assigned to `wells.WI`, and is not recomputed if `K` later changes. (A `WellModel` mixin, à la `Plot2D`, was tried and rejected.)
  - **Configure by assigning records**: `model.wells = [dict(xy=..., rate=...), ...]` (or `ResSim(wells=[...])`, or a `dict` keyed by name) — `xy` or `path`, `rate` and/or `bhp`, `rw`/`skin` or `WI`, `name` — which `Wells.from_records` assembles into the arrays, grouping included. The records are **read, not retained**: the arrays are the whole of the configuration (one representation, nothing to fall out of step), and they stay writable by hand, which HistoryMatching relies on.
  - **A well may span several completions** (e.g. one per cell of a `well_path`), and it is the *completions* that the model assembles and indexes everything by. So `nComp` counts the rows of `xy`/`rates`/`actual_rates`, whereas `nWell` counts wells; `group` maps the former to the latter, and `names` names them. The grouping serves the *reporting* alone (`rates_by_well`, the plot labels) — the physics never groups, and `group` may be left `None`, meaning one well per completion.
  - `Wells.__setattr__` is the wells' single normalization layer (`from_records` routes its assignments through it): `xy` is snapped to the nearest grid node and defaults to an empty `(0, 2)`; `rates`/`bhp` are reshaped to `(nComp, nTime)`; `WI` broadcast to `(nComp,)`; `group` to an int `(nComp,)`. Snapping needs a grid, so a `Wells` built standalone (`ResSim(wells=Wells(xy=..., rates=...))`, as the tests do) is normalized again when `_bind` attaches it. The back-reference `_grid` is typed `Grid2D`, not `ResSim`, to keep the dependency one-way; being underscored, `AlignedRepr` also keeps it out of the `repr`.
- **`Plot2D`** (`plotting.py`): plotting mixin (fields, streamlines, well markers).
- **`tlm`** (`tlm.py`): the hand-derived **tangent linear model** of one `time_stepper` step, wrt the *state* `(S, P)` only (parameters and controls fixed) — the building block for adjoint gradients wrt `S0`/`P0`, which is what it exists for. Three free functions: `linearize(model, dt, S, P, k)` *recomputes* the forward step by calling the model's own methods (checkpointing off the `(SS, PP)` that `sim` returns, so the forward is untouched and records nothing) and returns a `Tape` of intermediates plus its own `splu` of the pressure matrix; `tlm_step(tape, dS, dP)`; and `tlm(...)` along a trajectory. **Keep `tlm_step` a straight-line sequence of `M @ x` (sparse `M` on the tape), `a * x` (vector `a`) and `tape.solve(x)` statements** — no index gymnastics, no branching on the perturbations — because the adjoint is meant to be written by reversing and transposing it statement by statement (`solve` is self-adjoint, `A` being symmetric). To that end the 5-diagonal assemblies are recast on interior-face operators (`face_operators`: `Grad`, its transpose the divergence, `Sum` for the harmonic average, and the upwind selector `Up`), which `tests/test_tlm.py` checks against `TPFA`'s fluxes and `upwind_diff`. Discrete decisions (`nT`, upwind directions, flux signs) are frozen at the linearization point. Explicit scheme only. Verified against central finite differences (~1e-8 relative) on incompressible/compressible/BHP configurations; if the forward physics changes, the TLM must follow (the FD test will say).
- **`AlignedRepr`** (`_repr.py`): the `repr` mixin shared by `ResSim` and `Wells` (arrays summarized, nested reprs indented). Its own module because `wells.py` needs it too, and importing from `__init__.py` would be circular. It replaced `struct-tools`' `NicePrint` (as `Fluxes` and the `_wells_now` dict replaced its `DotDict`), that dependency having been dropped.

`examples/` holds the runnable illustrations; they
double as the regression tests. Each is a plain top-to-bottom script whose only concession
to the harness is a final `__digest__` dict of the values to be checked, and the guarded
`if __name__ == "__main__": show()`. `tests/test_examples.py` runs them all with `runpy`
(so `show()` is skipped, but the plotting *is* exercised) and compares a fingerprint of
`__digest__` with `tests/references.py` (regenerate that table with
`uv run python tests/test_examples.py`, but only if the change is intended).
`examples/buildup.py` is the one posed in **metric** units (the rest leave their units unnamed),
and reads its permeability back off the semilog derivative, as a well test does.
`tests/test_compressible.py` and `tests/test_units.py` are different: structural/physics properties, no figures.
