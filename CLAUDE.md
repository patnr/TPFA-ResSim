# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**MiniRes** (renamed from TPFA-ResSim, 2026-09-10, before the PyPI release): in code always lowercase -- the distribution and the import are both `minires` -- and in prose always "MiniRes" (README titles, docs headings, papers, talks); the class stays `ResSim`. The **GitHub repo is `patnr/MiniRes`** (CamelCase, renamed 2026-09-10 from `minires`): it is a display name, not an identifier, and matches the author's other project repos; GitHub resolves either case, so old clone URLs and pins keep working. Consequently the docs (GitHub Pages) live at <https://patnr.github.io/MiniRes/> -- mixed-case host path, lowercase page names (`.../MiniRes/minires.html`). A 2D, two-phase (water/oil), immiscible toy reservoir simulator using two-point flux approximation (TPFA), translated from the Matlab codes of Aarnes, Gimse & Lie (kept in `matlab_codes/`, paper in `refs/aarnes2007introduction.pdf`). Incompressible by default (`ct = 0`), with optional slight compressibility (`ct > 0`, backward-Euler accumulation term in the pressure equation, and the corresponding storage term in the transport equation, charged to the phases in proportion to their saturation — ref `ResSim.storage_rate`). The Python code is verified to reproduce the Matlab output — the regression values in doctests and tests encode this, so do not "fix" numeric expected values unless the physics intentionally changed.

## Downstream usage

The main consumer is [patnr/HistoryMatching](https://github.com/patnr/HistoryMatching) (locally at `~/P/HistoryMatching`), an ensemble history-matching tutorial that uses `ResSim` as its forward model. Consequences for changes here:

- It pins this repo by **git commit hash** in its `requirements.txt` (with a commented-out `-e` local-path line for development), so changes here don't break it until the pin is advanced — but breaking changes should be flagged so the pin advance can be coordinated. Its notebooks were **brought up to the v0.3.0 API on 2026-09-10** (the rename, the `(S, P)` tuple from `sim`, and the unified signed-rate wells), so its pin now needs advancing past the rename; the pin it carries is pre-history-rewrite and will need re-setting after that. What the port did, and what a future change here should therefore not be surprised by:
  - `HistoryMatch.py` configures `model.wells` with records and reads the producers off `wells.signs < 0`.
  - `Optimise.py` keeps its inj/prd vocabulary in a **notebook-local shim** (`INJ`/`PRD` name prefixes, `_rows`, `get_wells`, `set_wells`, `nInj`, `nPrd`, and `remake` dispatching `inj_*`/`prd_*` kwargs) — so it depends on `Wells.names` being per-well and on records being accepted for reconfiguration, but *not* on any inj/prd split here.
  - Its rate balance is enforced by a `well_controls` override (`BalancedRates`), which replaced the pre-`sim` rescaling and the v0.2.0 `dynamic_rate` mention.
  - `struct-tools` is now declared in its own `requirements.txt` (it used to arrive transitively from here).
  - The port is verified to reproduce the pre-port results: at full scale all three of its accuracy tables agree to the 4 printed decimals, and array-by-array the two runs agree to <1e-6 relative (the residue is the CG-preconditioned pressure solve's round-off, amplified by the *iterative* smoothers).
  - It was also what showed the residual assertion in `_solve_pressure` to be too tight — ref `active` below.
- Its de facto API surface is wider than `sim()`: the well config (`model.wells.xy`, `model.wells.rates`, ..., incl. the singleton time-broadcast behaviour), grid conversions (`xy2ind`, `ind2xy`), `shape`/`Nxy`, and the plotting mixin (`plt_field`, `plt_production`, `anim`). Notably it **mutates `minires.plotting.styles`** to register its own field styles — treat that dict and the `plt_field(style=...)` mechanism as public API. (The `unit` key added to `styles["default"]` is therefore optional and merge-safe: a style dict lacking it inherits the `None`.)
- Ensemble forecasting is why `ResSim` is OOP with per-instance state (see below), and why `sim` accepts `pbar=False`: many instances/runs, no shared mutable state, quiet loops.

## Commands

Dev environment is managed with uv (`uv sync`), but a plain `pip install -e .` also works. Note: `mise.toml` sets `UV_PROJECT_ENVIRONMENT` so the venv lives at `~/.cache/venvs/<repo directory name>`, not in-project — if mise isn't active in your shell, export that variable before running uv to avoid creating a duplicate `.venv`.

Plain `uv sync` installs the default (`dev`) group, i.e. everything. CI instead installs
only what it runs, via the narrower `test` and `docs` groups that `dev` includes — which
keeps the interactive tools out of the CI environment, notably `pdbpp`, whose shadowing of
the stdlib `pdb` that pytest and `doctest` import can break *collection* on an interpreter
it dislikes. It does the installing and the running in **one** step, e.g.
`uv run --locked --no-default-groups --group test pytest`: since `uv run` syncs
implicitly, a separate `uv sync` step would have to be undone with `--no-sync` in the
next, stating the group selection twice — so don't reintroduce one. Locally none of this
applies: plain `uv run` is right (as the commands below), its implicit sync converging on
the `dev` group you want.

## Architecture

The package is eight files; the physics lives in `minires/core.py`. `__init__.py` is only the README docstring plus the re-exports, and its `__all__` doubles as pdoc's table of contents: `ResSim` is documented on the package page (beside the README), and a submodule gets a page only if listed there -- `core` deliberately is not, since pdoc would otherwise document `ResSim` twice (nor are the other re-exports, documented in their home modules).

- **`ResSim`** (`core.py`) is a dataclass composed by multiple inheritance: `ResSim(AlignedRepr, Grid2D, Plot2D)`, and *composing* a `Wells` (`wells.py`). OOP is used (rather than passing dicts) so ensemble forecasting (as in HistoryMatching) can hold independent instances whose parameters don't influence each other.
  - `sim(dt, nSteps, S0, P0=None)` is the entry point, returning the `(S, P)` saturation and pressure trajectories: it loops `time_stepper`, which per step solves pressure (`TPFA()` → sparse direct solve; elliptic if `ct == 0`, else parabolic backward-Euler) then transports saturation with either the explicit upwind scheme (`saturation_step_upwind`, sub-steps from a CFL estimate) or the implicit Newton–Raphson scheme (`saturation_step_implicit`, halves sub-dt until convergence).
  - Method names reference listings in the paper (e.g. `TPFA()` = Listing 1, `Fluid.RelPerm()` = Listing 6).
  - **The fluid is one object, `fluid`** (`fluids.py`): a `Fluid` dataclass holding the viscosities `vw`, `vo` and the Corey parameters `swc`, `sor`, `nw`, `no`, `krw0`, `kro0` (defaults = unit viscosities, the paper's quadratic curves), and computing from them the mobilities `RelPerm`/`dRelPerm` (Listing 6; the normalized saturation `rescale_sat` **clipped** to `[0, 1]`, so odd exponents cannot make a phase mobile with the wrong sign below its residual, which `examples/egg.py` needs: the Egg deck starts water below connate) and the water fractional flow with its derivative, `fractional_flow(s)` and `dfractional_flow(s)`. These are the **one** implementation of $f_w$: both transport schemes, `estimate_1CFL`, the adjoint (`tlm`) and the examples' water cuts all call them. They are two methods, not one returning `(fw, dfw)`, because the upwind sub-step is the hot loop and wants $f_w$ alone: a 64² waterflood at $M = 5$ took 12600 sub-steps for 20 pressure solves, and the derivative in each cost as much as everything else (0.64 -> 1.25 s, profiled 2026-09-10) -- so **do not fold them back together**. Curves of another shape (e.g. tabulated) are a `Fluid` subclass overriding `RelPerm`/`dRelPerm`, assigned to `model.fluid`; `tests/test_fluids.py` has a `Linear` one. `__setattr__` normalizes `fluid` like `wells`: `None` -> a fresh `Fluid()` (per instance -- no shared default across an ensemble), a `dict` -> `Fluid(**d)`, anything else passes through. `ct` stays on the model: it is the *total* (rock + fluid) compressibility, and enters the pressure equation with `por`. The grouping was weighed against the alternatives (2026-09-10): the rock arrays (`K`, `por`, `active`) and the grid stay flat because HistoryMatching assigns `model.K` and reads `model.Nx`; `name`, `cdarcy`, `cached_precond` are singletons of their kind. A curves-only group (`kr`, a `Corey`, with the viscosities left on the model) was built first and superseded by this one, the user preferring one fluid object carrying the Listing 6 methods to a bare parameter bag. The clipping is why the *implicit* scheme's regression values agree with the Matlab output to 3-4 decimals rather than 5 (its Newton iterates pass outside the unit interval; ref the comment in `tests/references.py`) -- do not "fix" that by removing the clip. The CFL bound of the explicit scheme (`estimate_1CFL`) is 1.5 times the maximal fractional-flow slope, `dfractional_flow(ss).max()` over 1001 samples of the mobile range, inline (a `minimize_scalar`-refined `dfw_max` method was written and removed as over-built for one number under a safety factor; before `fractional_flow` existed it was the steepest chord of $f_w$ over the same grid -- same numbers to the sub-step, the references did not move; the sampling undershoots an interior peak by O(1e-6), so `tests/test_transport.py` sets the least purposeful `dt` margin at 1e-5, not 1e-6), which equals the paper's `3/(1 - swc - sor)` for the defaults at equal viscosities and is larger otherwise -- so it follows whatever curves are set.
  - **What stays here, of the wells**, is what couples them to the reservoir or to the linear system: `assemble_wells` (which writes the source field `_Q` and the bundle `_wells_now`), `realize_bhp`, `bhp` (needs `RelPerm`), and the `well_controls` hook. Everything else is `wells.py`. `ResSim.nComp` forwards `Wells.nComp`, the equations being assembled per completion.
  - **Wells are one unified set** — there is no code-path distinction between injectors and producers. `wells.rates` is **signed**: positive injects (water), negative produces (at the cell's fractional flow); the transport step discriminates by the sign of `_Q`, not by well identity. A BHP-controlled well's flow direction is likewise emergent (`realize_bhp`), and plot markers are inferred from the sign of the rate spec. `wells.actual_rates`/`actual_bhp` are single `(nComp, nSteps)` arrays.
  - **`__setattr__` does normalization magic**: scalar `K` is broadcast to shape `(2, Nx, Ny)`; `K`/`por`/`active` get their grid-shaped defaults here when left `None` (which is why there is no `__post_init__`); `active` is also checked for connectedness here, and its first cell recorded as the pin (`_pin`); and `wells` accepts either a `Wells` or the records to build one from, binding it to this model either way. The well arrays' own normalization is `Wells.__setattr__`. When `ct == 0` (and no BHP-controlled well), the rates must sum to zero at every time index (asserted in `time_stepper` — otherwise mass imbalance would silently leak in the SW corner). With `ct > 0` the imbalance is absorbed by storage (enabling e.g. primary depletion by a lone producer).
  - **Inactive cells** (`active`, a bool `(Nx, Ny)` mask, default all `True`) are the one departure from the plain rectangle, and are handled *without* fudge factors, so that conditioning and the CFL are untouched: the faces to them get zero transmissibility (in `TPFA`, and omitted outright by `tlm.face_operators`), their rows of the pressure system are identity rows (rhs = previous `P`), and their pore volume is `inf` (`pore_volume`, used by both transport schemes and `estimate_1CFL` via division), so their state is carried through unchanged. Do **not** implement a mask via tiny `K`/`por` (ill-conditioning, CFL collapse). **Disconnected regions are not detected.** There is one pin (`_pin`, the first active cell, hence still cell `0` when all are active) and the global rate balance of `_validate`; a second region is thus a singular block when `ct == 0`, which is *fine* if its own rates balance (or it has no wells, or a BHP well), and otherwise makes the solve return O(1e14) garbage rather than raise -- so `_solve_pressure` asserts the relative residual of the direct solve (`<= 1e-6` -- loose because the achievable residual degrades with the permeability contrast: HistoryMatching's log-normal ensembles reach 6e-8, which the original `1e-8` cried wolf on; O(1e-14) normally, O(1) then, deterministically: no `P` can cancel a rhs component along a region's constant vector). That 2-line assertion replaced, in turn: per-region pins and balances, a `csgraph.connected_components` assertion, and a "cursory pressure step" connectivity check built from a factored `TPFA` -- all judged too much code; the message of the commit that introduced `active` recounts the attempts (`git log --grep 'Inactive cells'`). Wells in inactive cells are refused. The arrays keep the full grid shape throughout (HistoryMatching's `Nxy`-length state vectors and `xy2ind` are unaffected); plots mask them (`plt_field`, which also gained `cellwise=True`: `pcolormesh` on the same colour levels, exact about cells where `contourf` blurs). Pinned by `tests/test_inactive.py` and two masked configs in `tests/test_tlm.py`; illustrated by `examples/inactive_cells.py`. Non-uniform, curvilinear or unstructured grids remain out of scope (the 5-diagonal assembly and `reshape` are hard-coded).
  - `well_controls(S, P, k)` is the designed override point (patch/subclass) for feedback control (e.g. shutting wells based on saturation): it returns `dict(rates=..., bhp=...)`, so an override can set the wells' *modes* too, thereby approximating the control-mode switching (e.g. a rate target with a BHP limit) that the model does not do natively — ref `examples/well_control.py`. Note that with `ct == 0` an override must keep injection and production balanced. It replaces the `dynamic_rate` hook of v0.2.0.
  - **`cdarcy`** is the whole of the units story: the equations carry **no conversion factors**, so any *coherent* system (SI, or the examples' unnamed `1`s) just works, and a *practical* one (metric: m, day, bar, mD, cP) needs only this constant, $C = u_k u_p u_t / (u_μ u_L^2)$ ($0.008527$ for metric, i.e. ECLIPSE's `CDARCY`). It enters at exactly **two sites** — the transmissibilities in `TPFA` and the well index in `peaceman_WI` — while the `ct` accumulation term, the transport scaling and `estimate_1CFL` are built from those and were already consistent, so **do not add factors elsewhere**. The rate unit is thereby forced to $u_L^2/u_t$, an *areal* rate (per unit thickness); $C$ neither names nor determines the units, being one scalar over five choices. Pinned by `tests/test_units.py`, which poses one reservoir in SI, metric, field and lab units and demands agreement. Deliberately *no* unit machinery: no `UnitSystem`, no registry, no plot labels — a `UnitSystem` + label layer was written and rejected as over-built.
- **`Grid2D`** (`grid.py`): rectangular grid geometry and the coordinate/index conversions (`xy2ind`, `sub2xy`, ...). Also holds `Fluxes`, the `(x, y)` face-flux container that `TPFA` returns and the transport step consumes -- here rather than in `core.py` because its content is grid-shape information, and because in `core.py` it had to precede `ResSim` (its annotations use it), making it the first thing on the package page. Index ordering is **C-major (numpy default), unlike the Matlab original**: `x` is the first axis, so printing a field matrix shows x as the row index, whereas plots show x left→right, y bottom→top. This ordering is hard-coded in the simulator via `ravel`/`reshape`.
- **`Wells`** (`wells.py`): the wells, as a dataclass held at `model.wells` — the flat, per-*completion* arrays (`xy`, `rates`, `bhp`, `WI`, `group`, `names`, `actual_rates`, `actual_bhp`) plus the reporting derived from them (`nComp`/`nWell`, `rates_by_well`, `signs`, `at_time`). Alongside it, three **free functions** — `peaceman_WI(model, xy, rw, skin)`, `well_path(model, vertices, rw, skin)` and `aquifer_WI(model, xy, faces)` — taking the model for its grid, `K` and `active`. Deliberately not methods: they are *calculators*, not accessors, and the signature says so — what they return must be assigned to `wells.WI`, and is not recomputed if `K` later changes. (A `WellModel` mixin, à la `Plot2D`, was tried and rejected.)
  - **Configure by assigning records**: `model.wells = [dict(xy=..., rate=...), ...]` (or `ResSim(wells=[...])`, or a `dict` keyed by name) — `xy` or `path`, `rate` and/or `bhp`, `rw`/`skin` or `WI` or `aquifer`, `name` — which `Wells.from_records` assembles into the arrays, grouping included. The records are **read, not retained**: the arrays are the whole of the configuration (one representation, nothing to fall out of step), and they stay writable by hand, which HistoryMatching relies on.
  - **Aquifers are wells, not boundary conditions.** `aquifer_WI(model, xy, faces="WESN")` is the half-cell transmissibility of a cell's boundary faces (to an inactive cell or off-grid; `faces` leaves sealed edges out, as it must on a 1D strip), and `dict(xy=contacts, aquifer=True, bhp=p_aq)` makes the contact cells BHP completions with it — which is *exactly* the Dirichlet-face discretization, `realize_bhp` folding the flux into `_Q` so transport, `storage_rate`, the CFL and the adjoint (whose BHP terms cover it; a gradient wrt the BHP controls, when there is one, is the sensitivity to `p_aq`) all follow with no new code. So `TPFA` has **no** boundary-condition machinery, deliberately: a Dirichlet term there would need boundary fluxes in `Fluxes`, a boundary saturation in transport, a `storage_rate` change and new adjoint lines, for the same numbers. Mobility is the cell's total one (an injector's well model), not upwinded from the aquifer. A finite (Fetkovich) aquifer is a `well_controls` override (`examples/aquifer.py`); Carter-Tracy (a convolution) and periodic BCs were judged not worth it. The ring of markers is hidden by `plt_field(wells=dict(exclude=["Aq"]))` and the contact stroked along the faces by `plt_faces` (both built on `wells.boundary_faces`, which `aquifer_WI` also uses); the flow-reversal warning is left to fire. Pinned by `tests/test_aquifer.py` (1D: the pressure extrapolates to `p_aq` at the face) and an aquifer config in `tests/test_tlm.py`.
  - **A well may span several completions** (e.g. one per cell of a `well_path`), and it is the *completions* that the model assembles and indexes everything by. So `nComp` counts the rows of `xy`/`rates`/`actual_rates`, whereas `nWell` counts wells; `group` maps the former to the latter, and `names` names them. The grouping serves the *reporting* alone (`rates_by_well`, the plot labels) — the physics never groups, and `group` may be left `None`, meaning one well per completion.
  - `Wells.__setattr__` is the wells' single normalization layer (`from_records` routes its assignments through it): `xy` is snapped to the nearest grid node and defaults to an empty `(0, 2)`; `rates`/`bhp` are reshaped to `(nComp, nTime)`; `WI` broadcast to `(nComp,)`; `group` to an int `(nComp,)`. Snapping needs a grid, so a `Wells` built standalone (`ResSim(wells=Wells(xy=..., rates=...))`, as the tests do) is normalized again when `_bind` attaches it. The back-reference `_grid` is typed `Grid2D`, not `ResSim`, to keep the dependency one-way; being underscored, `AlignedRepr` also keeps it out of the `repr`.
- **`Plot2D`** (`plotting.py`): plotting mixin (fields, streamlines, well markers).
- **`tlm`** (`tlm.py`): the hand-derived **adjoint** of one `time_stepper` step, wrt the *state* `(S, P)` and the parameter `log K` (nothing else: `por`, `ct`, well specs and `WI` fixed; `well_controls` assumed open-loop). Free functions: `linearize(model, dt, S, P, k)` *recomputes* the forward step by calling the model's own methods (checkpointing off the `(SS, PP)` that `sim` returns, so the forward is untouched and records nothing) and returns a `Tape` of intermediates plus its own `splu` of the pressure matrix; `adj_step(tape, aS1, aP1) -> (aS, aP, alogK)`; and along a trajectory `adjoint(model, dt, SS, PP, dJ_dSS, dJ_dPP) -> Gradient(S0, P0, logK)`, seeded by the objective's partials wrt the *stored* trajectory (objectives on the well reports are not seedable directly — differentiate the well model into the seeds by hand). `adj_step` is the reversal and transposition, statement by statement, of the step's *tangent*, which is a straight line of `M @ x` (sparse `M` on the tape), `a * x` (vector `a`) and `tape.solve(x)` statements (`solve` is self-adjoint, `A` being symmetric); each line's comment names the tangent statement it transposes, and **a new term must be derived that way** — write its tangent statement, then transpose it. The tangent model (`tlm_step`, `tlm`) and the dot-product test that bound the two to round-off were written first and then removed as not needed by the user (commits `f4087fa`, `ce5efb8` have them) — resurrect them to debug a new term. To make the transposition mechanical, the 5-diagonal assemblies are recast on interior-face operators (`face_operators`: `Grad`, its transpose the divergence, `Sum` for the harmonic average, and the upwind selector `Up`), which `tests/test_tlm.py` checks against `TPFA`'s fluxes and `upwind_diff`. Discrete decisions (`nT`, upwind directions, flux signs) are frozen at the linearization point. Explicit scheme only. `linearize` **mutates the model** as a step does (`_Q`, `_wells_now`, `_pLU`) but leaves `actual_rates`/`actual_bhp` alone — documented in its docstring, pinned by a test. Verified by the gradient of a whole-trajectory objective against central finite differences (~1e-8 relative) on incompressible/compressible/BHP/1D-row configurations; if the forward physics changes, the adjoint must follow (the FD test will say). Illustrated by `examples/water_cut_gradient.py` and `examples/history_match_gradient.py`.
- **`AlignedRepr`** (`_repr.py`): the `repr` mixin shared by `ResSim` and `Wells` (arrays summarized, nested reprs indented). Its own module because `core.py` and `wells.py` both need it (importing it from the package root would be circular). It replaced `struct-tools`' `NicePrint` (as `Fluxes` and the `_wells_now` dict replaced its `DotDict`), that dependency having been dropped.

`examples/` holds the runnable illustrations; they
double as the regression tests, and are published in the docs (see **Docs** above). Each
is a plain top-to-bottom script whose only concession to the harness is a final
`__digest__` dict of the values to be checked, and the guarded
`if __name__ == "__main__": show()`. The folder's `__init__.py` is a docstring only — the
examples' README, in effect, rendered as the `examples` page of the docs, so cross-refer
to them as modules (`` `examples.buildup` ``), which pdoc links. Its module-level docstring
and the figures are what an example's page shows: its members (`model`, `dt`, ...) are not. `tests/test_examples.py` runs them all with `runpy`
(so `show()` is skipped, but the plotting *is* exercised) and compares a fingerprint of
`__digest__` with `tests/references.py` (regenerate that table with
`uv run python tests/test_examples.py`, but only if the change is intended).
`examples/buildup.py` is the one posed in **metric** units (the rest leave their units unnamed),
and reads its permeability back off the semilog derivative, as a well test does.
`examples/water_cut_gradient.py` and `examples/history_match_gradient.py` are the adjoint's
(`tlm.py`) illustrations: both seed `tlm.adjoint` through the water cut at the producers
(`Fluid.fractional_flow`/`dfractional_flow` give $f_w$ and $f_w'$), check the gradient against a finite
difference *in the script* (an `assert`, like `buckley_leverett.py` asserts its analytics),
and put both numbers in their `__digest__`; the latter also takes a few steepest-descent
steps, so it is the slowest example (~4 s).
`examples/logo.py` is the odd one out: a smiley cut out by `active`, for the picture alone (a logo); its
`aquifer` flag toggles the aquifer along the bottom (and rebalances the rates).
`tests/test_compressible.py` and `tests/test_units.py` are different: structural/physics properties, no figures.

`notebooks/` holds the two **browser demos**, deliberately *not* in `examples/`
(whose `[!_]*.py` glob is read by both `pdoc_template/build.py` and
`tests/test_examples.py`, neither of which can do anything with a `marimo.App`)
and deliberately **untested**: each is a dozen lines of the API the suite already
covers -- configure a model, `sim`, `plt_field` -- so the signal for drift is the docs
build, not pytest. Both are linked from the root README's "Python" bullet and from
`minires/README.md`.

- `colab.ipynb` is committed **without cell outputs** (small diffs; the figures
  appear on running it), and is opened by
  `https://colab.research.google.com/github/patnr/MiniRes/blob/main/notebooks/colab.ipynb`.
  It ends with `model.anim(...).to_jshtml()` in an `HTML`, which is the one thing
  it does that the WASM one doesn't.
- `interactive.py` is a [marimo](https://marimo.io) notebook: `uv run marimo edit
  notebooks/interactive.py` to work on it, and `uv run marimo export html-wasm
  notebooks/interactive.py -o docs/wasm --mode run -f` to build the WASM, which
  `.github/workflows/docs.yml` does as a *second* step after the pdoc build, into the
  same Pages artifact (hence <https://patnr.github.io/MiniRes/wasm/>). Its `wasm`
  dependency group is marimo alone, kept out of `docs` (a much heavier install, and CI
  runs the two steps under their own `--group`) but included in `dev`, so that `ty`
  can resolve `import marimo` and the notebook can be edited locally. The export
  writes ~28 MB in a few hundred files (marimo's frontend), which is why it is
  published and **never committed**.

Both notebooks install `minires` **from PyPI** (`micropip` cannot do `git+`), so
they only work once the planned release is out. Verified in a real browser (2026-09-11):
the whole stack runs in Pyodide -- scipy's SuperLU (`splu`/`spilu`/`cg`), matplotlib,
`mpl-tools` -- at some 2-5x native, i.e. ~0.4 s per slider move for the 32² x 28 steps
posed there (which is why it is 32², not 64²), after a ~30 s cold start to fetch
Pyodide + scipy + matplotlib. `interactive.py` guards its `micropip` call with
`sys.platform == "emscripten"` so that it still runs natively. Pitfall, if ever
installing from a *wheel* instead of PyPI: the URL must be **absolute** -- a relative
one is resolved against the worker, not the page, and micropip dies with `BadZipFile`.
